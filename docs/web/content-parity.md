# Content parity with `apps/legacy-next`

Phase 7 (M7.1) measured `apps/web`'s output against the production legacy
site and legacy's own generated corpus JSON. The frozen baseline this
compares against lives in `apps/web/scripts/parity/baseline/` (captured once,
before legacy is retired — see `capture-baseline.ts`); the harness that
checks against it is `apps/web/scripts/parity/check.ts` (`pnpm run parity`).
Known, accepted divergences are recorded in `expected-exceptions.json`
(regenerated by `generate-exceptions.ts`), so none of what's described below
can silently grow without the harness catching it.

## Route coverage: clean

2,865 legacy production URLs vs 4,999 built `apps/web` pages (5,000 including
the new `/404`): **zero legacy URLs are missing.** The D1 tree is a strict
superset — 2,135 URLs are new. No redirect map is needed for Phase 8.

## 379 legacy documents are now collection (TOC) pages

379 URLs that were full-text reading pages in legacy now render a card grid
of child documents in `apps/web`, because the corpus pipeline split their
content across multiple child documents in D1 (legacy's paragraph count for
these slugs ≈ the sum of their D1 children's counts, plus 1–2 for a heading
absorbed into a child's title).

**This is treated as an intentional improvement, not a defect** — finer
document boundaries are what keep the reader pages from being larger than
they already are (see the DOM-diet work in M7.3). No anchor forwarding is
implemented: the parent→child paragraph-offset mapping is only approximate
(that's exactly why the counts differ by 1–2 near the boundary), and silently
landing a reader on the wrong verse would be worse than landing them on a
TOC page with working links to the actual content.

**Consequences, recorded so M8.6 doesn't mistake them for incidents:**

- These 379 URLs went from full-text pages to thin TOC pages. A Search
  Console content-quality or "thin content" signal on them during the
  post-cutover watch is **expected**, not a regression.
- Any `#para-N` fragment on these 379 URLs now no-ops — the page has no
  matching id, so the browser just doesn't scroll. There is no way to reach
  a specific paragraph via a legacy deep link into one of these documents
  anymore; the reader has to navigate to the correct child document first.

The full list, with each parent's D1 children, is in
`expected-exceptions.json`'s `collectionized` key.

## Paragraph-count parity: 4 divergences, one of them a parity _win_

Of the 2,220 legacy documents that are still `document`-type nodes in D1
(2,599 total minus the 379 above), 2,216 have byte-identical paragraph
counts. The remaining 4:

| Slugs                                                                                                                     | Δ                | Cause                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `atthakatha/sutta/mn/mulapannasa-atthakatha/gantharambhakatha`, `tika/sutta/mn/mulapannasa-tika/gantharambhakathavannana` | web = legacy + 2 | Both are the **first document of a multi-part volume**. D1 attaches two leading paragraphs to it — `rend="book"` (the volume title, e.g. "Mūlapaṇṇāsa-aṭṭhakathā") and `rend="subhead"` (the part label, "(Paṭhamo bhāgo)") — that legacy's generator didn't surface on this specific document. Recorded as `book-part-heading`.                                                                                                                                                                                                     |
| `sutta/kn/culaniddesapali/parayanavaggo`, `sutta/kn/culaniddesapali/parayanavagganiddeso`                                 | swapped          | **Legacy defect, not a web bug.** Legacy's `…/parayanavaggo` (1,471 paragraphs) opens with "Pārāyanavagganiddeso"; legacy's `…/parayanavagganiddeso` (481 paragraphs) opens with "Khaggavisāṇasutto". D1 assigns "Pārāyanavagganiddeso" to `…/parayanavagganiddeso` (1,471 paragraphs) — matching the heading sequence in the source TEI XML, `data/corpus/romn/s0516m.mul.xml` (Vatthugāthā → 18 numbered sections → the niddesa). **Web is correct; legacy's slug↔content assignment for this pair is shifted by one document.** Recorded as `legacy-defect` — this belongs in the M8.2 stakeholder sign-off as a parity _improvement_, not a defect list. |

Every other legacy↔D1 document pair matches exactly, including paragraph
`id`s (`para-N`, 1-based), `rend`, `pts`, `cst`, and the Pāli text itself —
spot-checked in full for `sutta/kn/dhammapadapali/yamakavaggo` during the
investigation, and count-verified for all 2,216.

## `deriveReaderSections` and `#para-N` anchors

Separately from the above (a **data**-level comparison), the **rendered**
page can omit one more paragraph than what's stored in D1:
`deriveReaderSections()` (`apps/web/src/lib/corpus/reader.ts`) drops the
first paragraph whose `rend` is `chapter`/`title`/`subhead` _and_ whose text
equals the document's own title — avoiding a redundant heading directly under
the page's `<h1>`. This is unrelated to the `book-part-heading` case above
(that pair's extra paragraphs don't match the document's own title, so
`deriveReaderSections` doesn't touch them) and applies to any document in the
corpus, not just the 4 in the table. The parity harness's anchor-sample check
runs the real `deriveReaderSections()` function to compute the expected
`id="para-N"` set per document, rather than assuming a naive contiguous
`1..N` — a naive assumption would false-positive on every document that
drops a self-title heading.

## Stray non-Latin codepoints in 26 documents' source text

`checkDecisionC`'s canonical-script guard (SSR HTML must stay Roman/IAST —
Decision C) flagged 26 pages containing isolated Devanagari combining/vowel
characters (`ः` U+0903 VISARGA, `ौ` U+094C VOWEL SIGN AU, `ै` U+0948 VOWEL
SIGN AI) embedded as single stray characters inside otherwise pure-Latin
text — e.g. `abhisambuddhoः lokasmā` where the source clearly intends a plain
colon before "lokasmā" (a defining clause), not a Devanagari visarga. These
are isolated marks, not runs of readable Devanagari text, which rules out a
build-time transliteration leak (that would produce whole words/sentences in
the wrong script, not single stray combining characters).

This is a **pre-existing transcription artifact in the source TEI XML**,
predating the Astro migration — almost certainly from an input-method slip
during the original CST digitization, where a Devanagari IME briefly leaked
a combining mark into the Roman-script edition. It is out of scope for
`apps/web` to fix (that's a `data/corpus` / `apps/pipelines` concern, not a
web-app QA task) and is recorded verbatim as `nonLatinSourceData` in
`expected-exceptions.json` so the guard still catches a genuine _future_
transliteration leak without re-flagging these 26 known pages every run.

## Regenerating this data

If the corpus is reseeded (new D1 data) or the legacy baseline needs
recapturing:

```sh
# Once, only while apps/legacy-next + the production site still exist:
pnpm --filter @cs-tipitaka/web run parity:baseline

# After any reseed, or to refresh the exceptions against fresh data/build:
pnpm run build   # dist/ must be current — several checks scan it
node --experimental-strip-types apps/web/scripts/parity/generate-exceptions.ts
```

`generate-exceptions.ts` labels any _new_ count divergence it can't attribute
to a known cause as `"unexplained"` rather than guessing — treat that as a
signal to investigate before trusting the output, the same way the four
above were investigated paragraph-by-paragraph rather than assumed.
